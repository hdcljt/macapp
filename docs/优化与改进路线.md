## 二、现存缺陷与问题（按优先级）

优先级定义：**P1** = 发布前必须处理 / 线上用户直接受影响；**P2** = 健壮性/安全/明显体验缺口，建议 1-2 个迭代内安排；**P3** = 卫生类，择机处理。

### P1-1 无单实例锁，应用可被重复启动

- **位置**：`electron/main.ts`（全文无 `app.requestSingleInstanceLock` / `second-instance` 处理，grep 验证 0 匹配）
- **现象**：用户双击图标两次 / 从安装目录再次启动，会开出**两个独立实例**：两个窗口各自加载 `targetUrl`、各自写 `main.log`（并发 append 同一文件）、Windows 任务栏出现两个入口。
- **修复建议**：
  ```typescript
  const gotLock = app.requestSingleInstanceLock();
  if (!gotLock) {
    app.quit();
  } else {
    app.on('second-instance', () => {
      if (mainWindow) {
        if (mainWindow.isMinimized()) mainWindow.restore();
        mainWindow.focus();
      }
    });
    // ... 原有 whenReady 逻辑
  }
  ```
- **工作量**：约 0.5h。

### P1-2 发布元数据仍是模板占位值

- **位置**：`package.json` → `build.appId: "com.yourcompany.macapp"`、`author: "Your Team"`、`copyright: "Copyright © 2026 Your Team"`
- **影响**：
  - appId 是安装/升级/卸载的稳定标识，发布后再改会导致 NSIS 升级时被识别为「另一个应用」（旧版残留、桌面快捷方式失效）；
  - author 与版权信息会展示在安装器/系统属性中，正式分发必须替换为真实主体。
- **修复建议**：确定正式 appId（如 `cn.migu.suanli.assistant`）与版权主体，**在首次对外发布前一次性定稿**，此后不再变更。
- **工作量**：0.1h（但决策成本高，需尽早）。

### P1-3 `config.jsonc` 的 targetUrl 当前指向测试环境

- **位置**：仓库根 `config.jsonc:5` — `"targetUrl": "https://cloudrender-sche-test.migu.cn:10600/agent-user/assistant"`（且 localhost 开发地址被注释）
- **影响**：打包时该文件作为 bundled default 进入安装包（`extraResources`）。当前状态下执行 `npm run build`，**发布产物会内置测试环境地址**。
- **修复建议**（三选一，按团队流程取舍）：
  1. 发布前人工切换 targetUrl 并双人复核（最简单，但易漏）；
  2. 拆分 `config.test.jsonc` / `config.prod.jsonc`，构建脚本按 `NODE_ENV` 或 CLI 参数选择拷贝源（推荐）；
  3. CI 打 tag 时注入生产配置。
- **工作量**：方案 2 约 1-2h。

### P1-4 更新源（GitHub Releases）与实际分发环境存在矛盾

- **位置**：`electron/updater.ts:75-80`（feed URL 固定 `github.com/hdcljt/macapp`）、`package.json` `build.publish` 同源；而本仓库实际托管于**内网 GitLab**。
- **影响**：内网 / 出网受限环境下：
  - 启动时更新检查静默失败（仅 `log.error`，用户无感知——这本身是设计选择，可接受）；
  - **Windows 已发布版本将永远无法自动更新**（下载走 GitHub）；
  - 国内公网用户访问 GitHub 也常超时。
- **修复建议**：
  - 短期：明确分发对象的网络可达性；若以内网为主，考虑将更新 feed 切到 `generic` provider 指向内网静态服务器/制品库（Nexus/MinIO/nginx 目录）；
  - 中期：支持 `config.jsonc` 覆盖 update feed URL，使同一包可对接不同分发环境。
- **工作量**：generic feed + 上传脚本约 0.5-1 天。

### P2-1 配置校验失败时，打包版用户只看到「应用闪退」

- **位置**：`electron/config.ts` 三处 `process.exit(1)`（解析失败 295-316、迁移后校验失败 391-397、URL 派生失败 401-408）
- **现象**：dev 模式有终端输出错误详情；**打包版无终端**，用户双击图标后窗口一闪而过（甚至无窗口），`userData/logs/main.log` 里才有原因——普通用户不可能去看日志。
- **修复建议**：退出前用原生对话框展示错误（不依赖任何渲染进程）：
  ```typescript
  import { dialog } from 'electron';
  dialog.showErrorBox('算粒AI助手配置错误', err.message + '\n\n配置文件路径：' + configPath);
  process.exit(1);
  ```
- **工作量**：约 0.5h（三个 exit 点统一封装成 `fatalConfigError()`）。

### P2-2 contentView 成功加载后崩溃，用户无任何恢复手段

- **位置**：`electron/main.ts:208-213`（offline-first 的 `render-process-gone` 仅记日志）；`createBaseWindow` 中 `setMenuBarVisibility(false)` 且未注册任何应用菜单
- **现象**：这是审查文档确认过的设计边界（「成功后 offline-fallback 退出职责」），但当前后果是：线上页渲染进程崩溃 / 白屏后，用户**没有刷新入口**（无菜单、无快捷键、无右键菜单），只能杀进程重启。
- **修复建议**（不违背原设计边界，只补最小恢复能力）：
  - 注册隐藏的应用菜单并绑定 `CmdOrCtrl+R`（webContents.reload）与 `CmdOrCtrl+Shift+I`（dev 用）；
  - 或仅在 `render-process-gone` 时 `contentView.webContents.reload()` 一次（带退避，避免崩溃循环）。
- **工作量**：0.5h。

### P2-3 自动更新只在启动时检查一次

- **位置**：`electron/main.ts:381-392`（`setImmediate` 内一次 `checkForUpdates()`）
- **现象**：桌面助手类应用通常长驻。挂机数天的实例不会发现新版本，直到用户手动重启。
- **修复建议**：`setInterval` 每 24h 调一次 `checkForUpdates()`（其内部已含 dismiss 冷却判断，重复调用安全）；或结合 P2-2 的恢复菜单提供「检查更新」入口。
- **工作量**：0.5h。

### P2-4 窗口尺寸/位置不记忆

- **位置**：`createBaseWindow()` 每次都按 `config.jsonc` 的固定 `width/height` 创建，无状态持久化
- **现象**：用户把窗口拖到副屏、拉大后的布局，重启后全部丢失。
- **修复建议**：`userData/window-state.json` 保存 bounds + maximized，启动时恢复（业界标准做法，注意校验 bounds 在当前显示器可见区域内，防拔掉副屏后窗口「消失」）。
- **工作量**：1-2h。

### P2-5 contentView 挂载了完整 preload，远程页面可触达全部 IPC 面

- **位置**：`electron/main.ts:89-104`（`createUrlView` 与本地页共用同一 `preload.js`），远程 `targetUrl` 页面为 `sandbox: false`
- **分析**：远程 agent 页面实际**并不使用** `window.electronAPI`（它是标准 Web 应用）；但 preload 无差别注入意味着：
  - 若线上页面被 XSS，攻击者可调用 `updater.install()`（触发 quitAndInstall）、`retryOnline()` 等指令；
  - 违背「最小暴露面」原则。
- **修复建议**：`createUrlView` 不挂 preload（`webPreferences: {}` 即可）；`will-navigate` / `setWindowOpenHandler` 拦截逻辑在主进程，不依赖 preload，移除无副作用。
- **工作量**：0.5h（需回归验证线上页功能不受影响）。

### P2-6 macOS ATS 全量放行任意网络请求

- **位置**：`package.json` → `build.mac.extendInfo.NSAppTransportSecurity.NSAllowsArbitraryLoads: true`
- **分析**：当前 `targetUrl` 已是 https，全量放行没有必要；放宽 ATS 会在安全审计中被标记。
- **修复建议**：删除 `NSAllowsArbitraryLoads`，如需兼容 http 局域网地址，用 `NSExceptionDomains` 精确放行。注意验证 http://localhost 开发场景（Electron 对 localhost 默认豁免，通常无影响）。
- **工作量**：0.25h + 打包回归。

### P2-7 代码签名缺失的连锁问题（中长期）

- **现状**：macOS ad-hoc 签名（每次构建指纹不同，首启需绕 Gatekeeper）；Windows NSIS 完全未签名。
- **影响**：
  - Windows：SmartScreen 拦截「未知发布者」，防病毒软件误报率高（对内部分发是噪音，对外分发是硬伤）；
  - macOS：无法启用 Squirrel 增量更新，更新体验是「下载完整 DMG 手动替换」；
  - 未签名 + `deleteAppDataOnUninstall: false` 组合下，卸载残留 userData 也无清理入口。
- **路线**：参考 [BUILD.md](../BUILD.md) 已列明的 Apple Developer ID + 公证 / Windows EV 证书步骤；代码侧无需改动（`identity` 配置项已预留），属流程与预算问题。

### P3-1 日志同步 IO + 无敏感信息过滤

- **位置**：`electron/logger.ts:82-90`（`appendFileSync`）+ 每次 write 都 `statSync` 检查轮转
- **分析**：当前日志频率低，无实际性能问题；但 `did-fail-load` 的 `validatedURL`、`will-navigate blocked` 的 URL 会原样落盘，若 targetUrl 体系内出现带 token 的 query，日志即泄露面。
- **建议**：低优先级；如需处理——写缓冲（攒行批量 flush）+ URL 落盘前剥除 query。

### P3-2 离线页数据与线上 UI 双份维护，必然漂移

- **位置**：`offline-app/src/data/assistantFeatures.ts` 首行注释「复刻自 macapp/src/data/features.ts」——6 个 AI 应用、三大功能区块、底部 Tab 全部硬编码两份。
- **分析**：线上改版（新增应用/改文案）后，离线页不会跟随，用户在「离线页 → 连上 → 线上页」之间会看到不一致的 UI。
- **建议方向**：接受漂移（离线页定位是兜底，不追求像素一致，仅同步大结构）；或构建时从线上仓库拉取数据文件生成；不建议离线页运行时请求线上数据（违背零网络依赖设计）。

## 三、工程质量优化项

### E-1 类型检查未接入构建链（P2）

- **现状**：`build-electron.js` 仅 esbuild（不做类型检查）；`tsconfig.json` 是 `noEmit` 但没有任何 script 调 `tsc`；`offline-app` 的 `build` 是纯 `vite build`，装了 `vue-tsc` 却没用。
- **后果**：类型错误不会打断构建，只能靠 IDE 提示。
- **建议**：
  - 根 package.json 增加 `"typecheck": "tsc --noEmit -p tsconfig.json && npm --prefix offline-app run typecheck"`；
  - offline-app 增加 `"typecheck": "vue-tsc --noEmit"`；
  - CI 在 build 前跑 typecheck。
- **工作量**：0.5h。

### E-2 无 lint / 格式化工具链（P2）

- **现状**：无 eslint / prettier / stylelint 配置（验证：仓库内 0 个 `.eslintrc*`）。
- **后果**：electron/ 与 offline-app/ 代码风格已经分裂（分号 vs 无分号）；多人协作后 diff 噪音增大。
- **建议**：引入 ESLint（typescript-eslint）+ Prettier，先以「增量格式化新代码」的低成本策略落地，避免一次性大 diff。
- **工作量**：0.5 天（含规则调优）。

### E-3 测试体系缺位（P2）

- **现状**：仅 2 个冒烟脚本 `scripts/test-config-migration.cjs`、`scripts/test-console-forwarding.cjs`，且**未接入 npm scripts**（`package.json` 无 `test` 命令，CI 也不跑）——可发现性几乎为零；无单测框架。
- **分析**：项目里有多个**纯函数极适合单测**：`validateConfig`（11 字段校验矩阵）、配置迁移（modify/applyEdits 保注释）、`logger` 轮转、`formatArgs`、`renderReleaseNotes`（DOM 解析）。
- **建议**：
  1. 先把两个冒烟脚本挂上 `"test": "node scripts/test-config-migration.cjs && node scripts/test-console-forwarding.cjs"`（5 分钟）；
  2. 引入 vitest，优先覆盖 config 校验/迁移（历史 bug 高发区）；
  3. CI 增加 test job。
- **工作量**：挂脚本 0.1h；vitest + 首批用例 1 天。

### E-4 文档漂移（P3）

- README「触发条件」写的是 push main/develop + PR + tag，实际 `.github/workflows/build-macos.yml` 仅 **tag `v*` + workflow_dispatch**；
- README「项目结构」未包含 `offline-app/`（v0.6.0 的核心新增）；
- README「自定义开发」引用的 `src/index.css`、`src/data/features.ts` 是旧仓库路径（现为 offline-app/src/...）。
- **建议**：随下一个功能迭代同步修订；或明确 README 的「使用手册」定位、把开发细节移入 docs/。

### E-5 依赖版本策略（P3，观察项）

- Electron 43 / TypeScript 7 / Vite 8 / Node types 26 均为最新大版本，成熟度与生态兼容性存在风险（如 TS 7 原生 port、Vite 8 的插件兼容）。
- **建议**：锁定当前组合不动，升级走「小步 + 回归清单」；CI 已有双平台产物校验，升级 Electron 时重点回归：WebContentsView bounds、updater 全流程、NSIS 安装升级。
